Final Year Project Management System
Database Design – Tables, Relationships & Business Rules
Purpose. This document records the current agreed database design for the FYP Management System. It is intended as a shared reference for the backend, database and frontend team members.
Status. This is the current V1 design. A few implementation details are deliberately left as decisions to confirm before the PostgreSQL schema is finalized.
1. System Overview
Students register/login individually and belong to an existing project team (for example, B1, B2, B3).
Admin maintains subjects, existing teams and guide assignments, manages users, views logs/status and has master-edit capability.
Faculty members belong to a subject and may be designated as coordinators by the admin. A coordinator can create tasks and define evaluation criteria.
A faculty member can guide multiple teams. Only the assigned guide evaluates a team's submissions.
Tasks are either individual or group tasks. Individual tasks are submitted by students; group tasks are submitted once by the team.
Even for a group submission, evaluation is performed separately for every student in the team.
Students receive in-app notifications and can communicate with faculty through messaging.

5. Important Business Rules
Coordinator is not a separate entity. A FACULTY member gets coordinator privileges through is_coordinator = true, with admin determining who is a coordinator.
Guide is not a separate entity. TEAM.guide_id references FACULTY.faculty_id.
Students register individually. Team membership is represented through STUDENT.team_id.
Teams already exist and are entered/maintained by admin.
A faculty member can guide multiple teams.
Tasks have two types: INDIVIDUAL and GROUP.
Individual tasks apply to the relevant students; group tasks apply to the relevant teams. The current design treats this as application/business logic rather than a separate ASSIGNMENT table.
For a group task, the team submits one file, but every student in that team must be evaluated individually.
submitted_by_student_id identifies who uploaded the submission; it is not the student receiving the evaluation.
Only the faculty member assigned as the team's guide evaluates that team's submissions.
Evaluation criteria define maximum marks. Awarded marks are stored separately for each student/criterion evaluation.
Total marks should be derived from the evaluation criteria rather than duplicated as a stored field.
Students need in-app deadline/status notifications.
Students communicate with faculty through the messaging feature; student-to-coordinator messaging is not a stated requirement.
Admin needs usage logs and master-edit capability, including correcting deadlines/submission-related records when authorized.

7. Important Implementation Notes
Group vs individual submission rules should be enforced by the backend and, where practical, by database constraints/indexes so the UI cannot be the only protection against duplicate submissions.
For a group submission, submitted_by_student_id records the uploader and team_id records the team. The EVALUATION rows then identify each student individually.
Authentication details are not fully finalized yet. Current requirements indicate university email and password, with USN also identifying the student.
File uploads may include DOCX, PPT, PDF, images and video. file_url should point to the eventual storage mechanism rather than storing large binary files directly in the relational table unless the team deliberately chooses that approach.
Admin master edits should be auditable. AUDIT_LOG should record who performed the action and what record was affected.
Notification delivery is currently assumed to be in-app/browser-based; no external push/email notification requirement has been finalized.

9. Current Schema at a Glance
Identity: USER → STUDENT / FACULTY / ADMIN
Academic structure: SUBJECT → FACULTY, TEAM → STUDENT, FACULTY → TEAM
Project workflow: FACULTY → TASK → EVALUATION_CRITERIA; TASK → SUBMISSION → EVALUATION
Communication/admin: USER → NOTIFICATION, USER ↔ MESSAGE, USER → AUDIT_LOG
